# Asympta Computer

Use the existing connected Asympta tools, not another app or hidden model. Preserve requested quality and mandatory acceptance; count validation and rework in efficiency. Never infer permission from a skill or invent unavailable tools.

## Choose the direct useful path

For a known small action, use its existing authorized tool. Discover unfamiliar actions compactly through `asympta_dispatch`; the live schema remains authoritative. Use `skills_sense` to select only relevant skills. No match means answer or work normally, not add a planning procedure.

For substantial outcome-first reframing, professional methods or cross-disciplinary investigation, load [Grounded Ambition](../grounded-ambition/SKILL.md). Preserve the original task, exact artifact, creative intent, privacy and budget. A harder target is a hypothesis, not a guarantee. Do not use this skill on every command or for transformation-only requests.

For consequential capability gaps, load [Capability Growth](../capability-growth/SKILL.md) to retain verified reusable learning within the same scope and authority.

## SubThread result inbox

For authorized SubThread work, let Asympta retain host completion records automatically. Do not require workers to send main an extra success message or replay their transcript. At a natural checkpoint, main reads a bounded inbox, expands only the needed result or evidence, and records a read receipt. Completion and acknowledgement never grant acceptance; keep independent source review and verification. Preserve applicable worker suspensions and permissions.

Use Linear only when requirements, external coordination, or explicit reporting need it. Keep routine internal result delivery inside Asympta, without a status-only model loop. Load [SubThread internal delivery](../cross-thread-orchestration/SKILL.md) when this workflow is relevant.

For native Codex context/fork updates and large structured receipts, load [Native context alignment](references/native-codex-context.md). Explicit compact/full `budget_chars` returns bounded views; `receipt_read` JSON pointers rehydrate needed evidence. This does not restore model-worker authorization.

## Durable work and actual evidence

Keep one visible task list for every multi-task request, including short requests, under one canonical Work. Capture every requested outcome, constraints, acceptance criteria, dependencies, ownership and finite budgets. Retain completed, failed, blocked and skipped work; update the list at real progress or scope changes. Reuse the native plan as a view of the same Work. Load [Plan-first orchestration](../plan-first-orchestration/SKILL.md) for the compact workflow.

Create new multi-task Work with `completion_contract:"verified"`. Separate execution, technical `verification_of` and `acceptance_of` rows, with explicit `acceptance_criteria`. Pin each attempt's revision after start/reset and before its execution or check; submit that retained revision with evidence. A stale token requires a fresh check, never a new token for old output. Require `work.acceptance.accepted:true` before claiming strict completion. Tool success, legacy Done and skipped work do not establish acceptance. Follow the live schema and [Task verification and acceptance](references/task-verification-acceptance.md), including fallback for unsupported servers.

Use bounded independent read batches only where supported by the current server; never insert writes, shell commands or remote actions into a read-only batch. Serialize conflicting writes and isolate independent workers.

A tiny success receipt or tool acknowledgment is not proof that the user's outcome was accepted. Preserve the full evidence outside model context and expand only relevant failures. Read authoritative state before retrying a timed-out mutation; never blindly repeat uploads, pushes, publication or UI actions. Keep source/version identity and negative results.

Use the existing singleton Terminal Dashboard to observe separately sourced Work and provider progress. Do not create another native Dashboard, take over active sessions or invent continuous execution. For Apple apps, implement a related batch, perform necessary release checks, distribute to the existing authorized TestFlight group, update the physical app and test the complete scene on that exact build. Compilation alone is not user-scene acceptance.

## Quality and boundaries

Use real images, references and appropriate human review for creative quality; a model self-score is not visual acceptance. Preserve locked style, typography, artwork and interaction requirements. Use original sources or data and independent validation for research. Report actual source revisions, changed artifacts, tests and remaining blockers without claiming unmeasured speed, accuracy, cost or creativity gains.

Treat **Token saving = Quality** as a requirement to preserve all mandatory quality while reducing measured usage. Among equally accepted outcomes prefer lower total usage, then end-to-end speed and reliability. Report exactly three metrics: **Speed**, **Accuracy / Quality**, and **Usage Saving**. Include all attempts, agents, retries, verification and acceptance overhead; missing telemetry stays unknown. Keep 10× a target until a matched comparison at equivalent accepted scope proves the specific metric. Use the measurement definitions in the task acceptance reference.
