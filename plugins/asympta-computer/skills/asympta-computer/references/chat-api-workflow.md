# Chat-first routing, bounded workers and acceptance

Updated 2026-10-29. Apply this to substantial Asympta fixes, features, UI/UX, characters, scenes and validation. Start in Chat when requested; retain current task and standing authorization. Treat the host interface, model, execution environment and billing pool as separate facts.

## Choose one useful route

Use native Chat tools for research, reasoning, code authoring, image generation and review when sufficient. Use Asympta for Mac/private repository/Xcode/device/Blender access and durable deterministic execution. Use Codex for a bounded repository edit/test loop when its expected quality or completion-time advantage justifies its allowance or API cost. Keep simple sufficient native operations direct.

Discover the live manifest and exact action schema. Use `workflow_route` only when advertised, and bind its decision to canonical Work. A route decision does not launch or complete its chosen work. Discover `openai_task` separately; its selector is `operation`, not the outer dispatch/port `op`. A deployment candidate or a documentation entry is not proof that a live action exists.

This Chat/API workflow and bounded `openai_task` retain the `sol_or_astra` default and `gpt-6.1-sol` floor. A separately authorized general-API request may explicitly use `model_policy:"adaptive"` for Terra/Sol/Astra; preserve stronger pinned requirements and explicit model/effort choices. Never silently downgrade. Preserve **450000** compaction. Optional `verified_exact` reuse requires matching accepted output SHA, evidence, policy/task context and freshness; caller attestation permits reuse, not Work or device acceptance.

## Current bounded worker

The first `openai_task` implementation edits declared source files in an ordinary clean isolated Git worktree. Automatic verification is limited to protected explicit Node tests with caller-declared expected test names, using the existing offline sandbox. Repository command filters are rejected. Native builds, physical-device scenes and release remain separate host-owned stages. A worker result is `needs_review`, never accepted Work. Call/output/tool/input/time limits bound execution; they are not a guaranteed dollar cap.

Use `openai_capability` only when advertised: status performs no inference, and an explicit bounded Agents probe establishes listing access only. It does not establish managed execution, Mac support or grant coverage.

## Declare budgets truthfully

Keep regular Chat usage, shared Work/Codex allowance, API billed usage/credits and machine compute separately observable. Unknown grant eligibility or consumption stays unknown; an API key, model-list result, short receipt or local task count does not prove credit coverage or savings.

Use a finite request/call/token/spend and retry budget for paid workers. `api_authorized` is the host's truthful declaration of authorization from the present task plus valid session/standing instructions; it does not require asking the user again each run. Loading this guidance grants no new spending, publishing or scheduling authority. Do not create hidden routes or infer unlimited spending from a configured key.

Apply zero-Codex constraints to their named task or mission. For that scope, prohibit Codex/Work model turns and implicit fallback; route only to a permitted active Chat host, deterministic execution or expressly authorized API work. A dormant Chat handoff remains awaiting_host. Inspect child commands before describing them as model-free.

## Bind work and evidence

Use one canonical Work plan with current requirement revision, execution/verification/acceptance dependencies, owners and resources. Give a worker its work/step IDs, exact repository/base SHA, allowed files, acceptance criteria and budget. Use separate worktrees for concurrent edits and one integration owner. Lease shared GUI, capture and device resources; task parallelism never grants concurrent ownership of one iPad.

Prefer deterministic tools for builds, tests, conversion and waiting. Keep full logs outside the model context; retrieve concise receipts and relevant failure windows. Reuse idempotency keys after uncertain acknowledgements. Inspect an existing request/job before retrying; never duplicate an unresolved mutation or charge.

Choose the smallest sufficient acceptance set once per compatible batch. Bind evidence to source/build identity, requirement revision, test/fixture and device/OS. Recheck only relevant changes, actual failures, changed external state or mandatory gates. NOT RUN and missing evidence remain visible. ACK, build success, screenshots and author self-report cannot prove untested behavior. Independently review material changes.

## Preserve the actual Apple and visual gates

Follow the currently applicable TestFlight scene-validation instructions from the active environment. Retain the single **MuzhuSceneOperator**, one physical-iPad lease, exact installed TestFlight identity/build and required full-scene coverage. Do not add another runner or sideload to satisfy that acceptance gate. Keep real Pencil/thermal evidence distinct from simulated inputs and screenshots.

For art, inspect generated assets and actual in-app rendering/animation. Report implementation, testing, acceptance, upload, processing and installed verification separately. Preserve observed source/evidence and unresolved requirements in the final receipt. 10×/100× savings require matched accepted-task measurement including retries, children and handoff overhead.

Use [Chat-first handoff](chat-first-handoff.md) for transfer mechanics and [task verification and acceptance](task-verification-acceptance.md) for canonical completion. Neither a route nor a handoff replaces execution and objective acceptance.
